# OVE_TG004: Persist Telegram state in SQLite: pairing, offsets, dedupe window and callback ids

## 1. Summary

SQLite implementations of the three Telegram repositories with their migration: the single pairing row, active pairing code, polling state (offset, recent update ids, counters, bot info) and the server-side callback ids for inline buttons.

## 2. Context

T3: persist the highest processed `update_id` and a short window of recent ids so replays and restarts do not re-run commands. T4: inline button payloads are opaque ids mapped server-side. T1: single-use codes and global lockout must be atomic. The pairing and state tables are installation-wide; `telegram_callbacks` carries `workspace_id` and is Workspace-scoped (cascade: OVE_TG015).

## 3. Scope (in)

- One migration with four tables.
- Repository adapters implementing the TG001 ports atomically.
- In-memory fakes and contract suites.

## 4. Out of scope

- Pairing logic: TG003. Poller usage: TG005. Callback semantics: TG010/TG011. Cascade participant and restore sanitiser: TG015.

## 5. Detailed requirements

1. **Migration** `V202610131020__OVE_TG004__telegram_tables.sql` (the callbacks table is marked workspace-scoped with the comment `-- workspace-scoped: yes` immediately above it):
   ```sql
   CREATE TABLE telegram_pairing (id INTEGER PRIMARY KEY CHECK (id = 1), chat_id TEXT NOT NULL, user_id TEXT NOT NULL,
     username TEXT, display_name TEXT, paired_at TEXT NOT NULL) STRICT;
   CREATE TABLE telegram_pairing_codes (id INTEGER PRIMARY KEY CHECK (id = 1), code_hash TEXT NOT NULL, salt TEXT NOT NULL,
     created_at TEXT NOT NULL, expires_at TEXT NOT NULL, consumed_at TEXT) STRICT;       -- at most one active code
   CREATE TABLE telegram_state (key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL) STRICT;
     -- keys: update_offset, recent_update_ids (JSON array, max 1000), wrong_attempts, locked_until, bot_info, counters:<name>:<yyyymmddhh>
   -- workspace-scoped: yes
   CREATE TABLE telegram_callbacks (id TEXT PRIMARY KEY, action TEXT NOT NULL CHECK (action IN ('approve_run','deny','route_pick')),
     approval_id TEXT, run_id TEXT, workspace_id TEXT, chat_id TEXT NOT NULL, message_id TEXT,
     payload TEXT, expires_at TEXT NOT NULL, used_at TEXT, created_at TEXT NOT NULL) STRICT;
   CREATE INDEX telegram_callbacks_approval ON telegram_callbacks (approval_id);
   CREATE INDEX telegram_callbacks_workspace ON telegram_callbacks (workspace_id);
   CREATE INDEX telegram_callbacks_expiry ON telegram_callbacks (expires_at);
   ```
2. `consumeCode(hash, now)` is one statement: `UPDATE telegram_pairing_codes SET consumed_at = :now WHERE code_hash = :hash AND consumed_at IS NULL AND expires_at > :now` and succeeds only when exactly one row changed; comparison of the hash is constant-time at the application level before the statement is chosen (hash equality via a prepared lookup, never string `LIKE`).
3. `claim(id, chatId, now)` is `UPDATE ... SET used_at = :now WHERE id = :id AND used_at IS NULL AND expires_at > :now AND chat_id = :chat` followed by a read; reasons `unknown|used|expired|wrong_chat` are determined by a second read only for logging (never returned to the sender in detail).
4. `rememberUpdateId` keeps the last 1000 ids in the JSON window (trimmed) in the same transaction as `setOffset` when called through `commitBatch({ offset, ids })` (one transaction per processed batch).
5. `incrementCounter(name, hourBucket)` upserts integer counters; no message content, sender id or chat id is ever stored in counters.
6. Callback ids are generated by the caller (ULID prefix `tcb`), 30 bytes at most; `purgeExpired()` deletes rows expired for more than 1 day, run by the poller hourly.
7. All repository methods return `Result`; SQL errors map to `data.*` codes; JSON values validated by zod on read (corrupt window means start with an empty window and a `warn`, never a crash).

## 9. Security and safety

- Atomic single-use semantics are implemented in SQL, not in process memory, so a crash or a second engine instance cannot double-use a code or a callback.
- Salted hashes only for pairing codes; the plain code never reaches the adapter.
- No content of foreign messages is persisted anywhere (T12: counters only).
- Parameterised statements; ids validated before use.

## 10. Errors and edge cases

- Crash between `setOffset` and processing: offset only advances in `commitBatch` after handling, so updates are re-delivered and deduped by the window.
- Window corrupt: empty window, offset still prevents old replays.
- Concurrent `claim` of one id from two presses: exactly one wins.
- Restore from backup: pairing and callbacks are cleared by the TG015 sanitiser.
- Very old callback rows: purged.

## 11. Acceptance criteria

- [ ] Given a valid code, When two `consumeCode` calls race, Then exactly one succeeds.

- [ ] `commitBatch` updates offset and window atomically.
