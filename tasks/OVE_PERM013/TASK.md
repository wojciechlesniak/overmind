# OVE_PERM013: Define the ApprovalRequest contract and its state machine

## 1. Summary

The shape of an Approval request (`id, runId, action, status, expiresAt` plus preview and binding data) and a pure state machine that makes approvals single-use, time-boxed and bound to the exact action. No Approval can be reused for a different action, Run or time.

## 2. Context

SPEC 14: `ApprovalRequest: id, runId, action, status, expiresAt`. Approvals are decided on the desktop or on Telegram (ADR 0006); the Owner sees a preview of the change (ADR 0022: CLI permission dialogs become Overmind Approvals with a diff preview). SR-34: approvals are bound to id, Run, action hash, expiry, single use.

## 3. Scope (in)

- `ApprovalRequest` zod contract, `ApprovalPreview` variants per `ActionClass`, `ApprovalDecision`.
- `transition(approval, event, ctx)` pure state machine and guard functions.
- Three events (requested, decided, expired) with `defineEvent`.

## 4. Out of scope

Use cases and storage (PERM014, PERM025), routes (PERM027), notification delivery (NOTIF, TG), UI (APPRUI).

## 5. Detailed requirements

1. **Entity**
   ```ts
   ApprovalRequest = { id: EntityId<'apr'>, workspaceId, runId, agentId, nodeExecutionId?: EntityId<'nex'>,
     action: { class: ActionClass, summary: string /* <=200, generated by engine from structured data, never from agent free text */,
               structured: ActionParams /* per class, strict */ , actionHash: string /* sha256 of canonical {class, structured, runId, agentId} */ },
     preview: ApprovalPreview, status: 'pending'|'approved'|'denied'|'expired'|'cancelled'|'consumed',
     requestedAt, expiresAt, decidedAt?: IsoDateTime,
     decision?: { by: 'owner_desktop'|'owner_telegram', scope: 'once', note?: string /* <=500 */ },
     consumedAt?: IsoDateTime, correlationId?: EntityId<'req'> }
   ```
   `scope` is always `'once'`: an Approval permits exactly one execution of exactly that action. (Telegram vs desktop differ only in `by`; neither can create a standing approval.)
2. **Previews** (`ApprovalPreview`, discriminated by `class`): `delete_files { paths: string[] (display paths, max 20), totalCount }`, `git_push { remote, branch, commits: {sha7, subject (<=100)}[] (max 10), forcePush: boolean }`, `publish { target, artifactName, version? }`, `external_message { channel, recipientDisplay (redacted), subject?, bodyExcerpt (<=500) }`, `payment { amount: string, currency, payeeDisplay }`, `new_domain { host }`, `budget_overrun { budgetKind, limit, projected }`. All strings bounded, control characters stripped, display paths `~`-relative or Workspace-relative, never absolute outside the Workspace. Previews are produced by the engine from structured data; untrusted text (commit subjects, message bodies) is marked `untrusted: true` and rendered as plain text by the UI/Telegram (SEC004, SEC008 T11).
3. **States and transitions** (all others illegal, returning `perm.approval_not_pending` or `perm.approval_expired`):
   `pending → approved` (decision approve, not expired, run still active), `pending → denied`, `pending → expired` (clock passes `expiresAt`, by sweeper or lazily on read), `pending → cancelled` (Run cancelled/finished, or requester withdraws), `approved → consumed` (the broker executes the action once), `approved → expired` (approval not consumed within `consumeWindow` = 10 minutes after decision, ASSUMPTION), `approved → cancelled` (Run ends before consumption). Terminal: denied, expired, cancelled, consumed.
4. **Expiry:** default `expiresAt = requestedAt + 30 min` (ASSUMPTION; per class override table in config: `payment` 10 min); max 24 h; the requester cannot choose a longer one. Expiry is evaluated against the injected `Clock` on **every** read and transition (lazy) in addition to the sweeper.
5. **Binding guards:** `canConsume(approval, { runId, agentId, actionHash, now })` is true only if `status==='approved'`, hashes equal, ids equal, `now < decidedAt + consumeWindow`. Any mismatch returns `perm.approval_mismatch` and leaves the state unchanged (and the use case writes a violation).
6. **Telegram constraint:** an approval decided with `by:'owner_telegram'` is valid only while its Run is the same Run (it always is, `runId` is part of the hash); there is no way to create a permanent effect from it. The state machine exposes `by` only for audit.
7. **Events:** `approval.requested` (payload: id, workspaceId, runId, agentId, class, summary, expiresAt, `notify: { sound: boolean, urgency: 'high' }`), `approval.decided` (id, status, by), `approval.expired` (id). No preview contents in events (consumers fetch via the gateway with scope), to keep secrets/long text out of the bus. Persisted: yes; audit: yes.
8. Contract check (ARCH008) strict objects, bounded lengths.

## 9. Security and safety

Replay and confused-deputy defences are encoded here: single-use (`consumed`), expiry (lazy and swept), hash binding to class + structured params + Run + Agent, and a consumption window. `summary` and `preview` are engine-generated from structured data (never copied from the agent's free text) to prevent a prompt-injected Agent from presenting a harmless description for a dangerous action ("approve: update README" for a force-push). A mismatch between the executed action and the hash never consumes an approval.

## 10. Errors and edge cases

- Decision arrives after expiry: `perm.approval_expired`, state becomes `expired`.
- Decision twice (desktop and Telegram at the same time): first wins; second gets `perm.approval_not_pending`.
- Run cancelled while pending: becomes `cancelled`; late decisions are rejected.
- Clock moves backwards: `expiresAt` comparisons use monotonic `Clock`, expiry never un-happens.
- Preview with a 10 MB commit subject: truncated to 100 chars.

## 11. Acceptance criteria

- [ ] Every legal and every illegal transition pair has a test (full matrix of 6 states x 7 events).
- [ ] `canConsume` fails for: different Run, different Agent, different class, different params (hash), after the window, twice.
- [ ] Previews are bounded; control characters and Markdown/HTML control sequences are neutralised in text fields (they are plain text; renderers must not interpret).
- [ ] Events validate against their schemas and contain no preview text.
- [ ] Contract snapshot committed.

## 12. Test plan

Table tests for the machine; property test: any sequence of random events from any state never reaches `consumed` twice and never leaves a terminal state. Hash stability test (key order). `pnpm vitest run packages/domain/src/perm/approval packages/contracts/src/perm/approval`.

## 14. Open questions and assumptions

- ASSUMPTION: expiry 30 min (payments 10 min), consume window 10 min. Needs the Owner's view; configurable via config section `perm.approvals` (ARCH005 proposal).
- Open: pending approvals when the machine sleeps: expiry uses the monotonic clock, which may not advance during sleep; default is to also compare wall time, so an approval pending across sleep expires if either clock passes the limit.
