# Overmind backlog: conventions

Authoritative rules for every task in `tasks/`. Read this file fully before writing or implementing any task.

This backlog contains **only task descriptions** (Markdown plus exported design images). Nothing in it has been built. Project setup, dependencies and configuration are described as tasks like everything else.

Language: English (ADR 0017). Domain terms follow `docs/GLOSSARY.md` (Polish source), with the English names in the table at the end of this file. UI copy visible in the design mocks is Polish; the implementation uses i18n keys with English as the default locale and Polish as the first translation.

---

## 1. Task identity and layout

- **ID:** `OVE_<AREA><NNN>`, for example `OVE_PAUSE001`. `<AREA>` is 2-6 uppercase letters from the area table in `PLAN.md`. `<NNN>` is a zero-padded 3-digit counter, unique within the area. IDs are never reused or renumbered. A cancelled task keeps its folder with `status: cancelled`.
- **Folder:** `tasks/<ID>/`
  - `TASK.md` (required): front matter plus the body sections in section 3.
  - `design.png` (only when the task has a visual specification): the crop of the exported design that this task implements. If there is no `design.png`, the task is about functionality (data, logic, contracts, infrastructure), and `design: none` is in the front matter.
  - `design-*.png` (optional): extra crops (for example a state variant or a zoomed detail).
- Shared, non-task material lives in folders that start with `_`: `_design/` (full views, HTML sources, `VIEWS.md`, `COMPONENT-INVENTORY.md`), `_template/`, `_manifests/`, `_proposals/`.
- `tasks/INDEX.md` and `tasks/DEPENDENCIES.md` are generated from the front matter. Do not edit them by hand.

## 2. Front matter (YAML) in every `TASK.md`

```yaml
---
id: OVE_PAUSE001
title: Imperative, specific title (max 90 chars)
area: PAUSE
kind: feature        # feature | ui | infra | contract | security | test | docs | spike | decision
size: S              # XS (<=1h) | S (1-2h) | M (2-4h). Never larger: split instead.
priority: P0         # P0 = MVP-critical path, P1 = MVP, P2 = post-MVP / later
mvp: true
status: todo         # todo | in_progress | in_review | done | cancelled
depends_on: []       # task IDs that MUST be merged before this one can start
soft_depends_on: []  # IDs that make it easier but do not block
provides: []         # named capabilities other tasks can reference, e.g. "api:pause.global", "ui:Button", "port:ApprovalRepository"
needs: []            # capability names this task consumes (every need must be provided by some task; the linker resolves them to depends_on)
owns: []             # paths/globs this task creates or edits EXCLUSIVELY
reads: []            # paths it only reads
design: design.png   # or "none"
design_source: ""    # e.g. "Main#canvas/node-tile (crop 410,420,330,170)"; empty when design: none
spec_refs: []        # e.g. ["SPECIFICATION 11", "SPECIFICATION 16.8"]
adr_refs: []         # e.g. [3, 21]
---
```

`blocks:` is generated by the linker and must not be written by hand.

## 3. Body of `TASK.md` (sections in this order, none omitted)

1. **Summary**: 2-3 sentences. What is built and why it matters.
2. **Context**: where this sits in the product, which Spec sections and ADRs drive it, which glossary terms apply. A reader with zero prior knowledge must be able to start.
3. **Scope (in)**: exact list of what this task delivers.
4. **Out of scope**: what is explicitly NOT done here, each with the ID of the task that does it (or "later / not planned").
5. **Detailed requirements**: numbered, testable, using MUST / SHOULD. Include data shapes (zod schema field lists, TypeScript signatures, SQL columns, API paths and payloads), algorithms, limits and defaults. Where the Spec says PROPOSED, state the default chosen and mark it `ASSUMPTION`.
6. **Design notes**: for UI tasks, describe what `design.png` shows (anatomy, tokens by name, states, exact copy strings with i18n key suggestions, spacing). List states that are NOT in the mock (empty, loading, error, hover, focus, disabled) and how to derive them from the design system. For non-UI tasks write "N/A, functionality only".
7. **Reuse**: components, utilities, ports and contracts this task MUST use (by name and task ID), and which new reusable pieces it MUST create and where. Duplicating something that already exists is a defect.
8. **Architecture and code placement**: target package and paths, layer (domain / application / adapter / UI), ports used or defined, and how the task respects SOLID, DRY, KISS and Clean Architecture (what depends on what).
9. **Security and safety**: always present. Cover trust boundaries touched, deny-by-default behaviour, secrets, untrusted input (prompt injection, paths, symlinks), audit logging, and failure behaviour (fail closed). If truly nothing applies, say why in one sentence.
10. **Errors and edge cases**: concrete cases and the expected behaviour for each.
11. **Acceptance criteria**: a checklist. Prefer Given / When / Then. Every requirement in section 5 maps to at least one item.
12. **Test plan**: which tests to write (unit, contract, integration, e2e, visual, a11y), their names, fixtures and the commands.
13. **Parallelization notes**: what can run concurrently with this task, which files are conflict hotspots, and the extension points to use instead of editing shared files.
14. **Open questions and assumptions**: anything the task author could not settle, with the default that implementers MUST use until the Owner answers. Never leave a task silently ambiguous.

Target length: 80-250 lines. Depth beats brevity: a missing detail costs a follow-up task.

## 4. Size and splitting rules

- One task = one coherent change an agent finishes in at most about 4 hours, normally 1-3. Roughly at most 400 changed non-test lines.
- A large view is never one task. Split it by layers and by region, in this order: (a) contracts and API, (b) static, props-driven UI with fixtures, (c) data wiring, (d) interactions, (e) empty / loading / error states, (f) accessibility and visual-regression tests.
- A task creates a reusable component only when it is the first user; if a second task needs the same thing, the second task depends on the first (never copies it).
- A task that would touch more than ~15 files in more than 2 packages must be split.

## 5. Parallel work by many agents

Several agents work at the same time. The rules prevent conflicts:

1. **One agent per task, one worktree per agent.** Branch `task/<ID>`, worktree `../wt/<ID>`. Claiming a task = pushing its branch. If the branch already exists, pick another task.
2. **File ownership.** A task edits only files under its `owns` paths (plus its own tests and stories). Editing a file owned by another task is forbidden. If it is needed, write a proposal file `tasks/_proposals/<ID>-<short-name>.md` describing the change and stop that part of the work.
3. **Extension points instead of shared files.** Shared aggregators are generated or auto-discovered, never hand-edited by feature tasks (details in `OVE_ARCH009`):
   - UI routes and nav items: each feature exports `feature.manifest.ts`, collected by `import.meta.glob`.
   - i18n: one namespace file per feature (`locales/<lang>/<feature>.json`).
   - Gateway endpoints: one route module per capability (`*.route.ts`), auto-registered.
   - Contracts: one file per entity under `packages/contracts/src/<entity>/`; barrels are generated.
   - Ports: one file per port under `packages/application/src/ports/`.
   - Events: one file per event type under `packages/contracts/src/events/`.
   - DB migrations: `V<YYYYMMDDHHmm>__<TASKID>__<name>.sql`, ordered by version string; never edit a merged migration, add a new one.
4. **Dependencies are explicit.** `depends_on` lists every task that must be merged first. A task whose dependencies are not all merged MUST NOT start. Anything depended upon is expressed as a contract (schema, port, component props) so work can start against a stub when the dependency is in review (`soft_depends_on`).
5. **Rebase, do not merge main.** Keep the branch rebased on `main`. CI must be green. A human merges.
6. **No scope creep.** If the work reveals a missing task, add a proposal file. Do not widen the task. (This mirrors ADR 0016: nothing is added from the agent's own initiative.)
7. **Do not weaken tests, lint or boundary rules to make a task pass.**

## 6. Architecture rules every task MUST respect

Full text: `OVE_ARCH001` (`docs/architecture/ARCHITECTURE.md`). Summary:

- **Layers (Clean Architecture):** `contracts` <- `domain` <- `application` <- `{workflow-runtime, gateway, adapters/*}` <- `apps/engine` (composition root). `ui-kit` depends on nothing internal. `apps/desktop` depends only on `ui-kit`, `api-client` and `contracts`. Nothing imports from `apps/*`. Adapters never import each other.
- **Domain and application contain no I/O.** All I/O (SQLite, filesystem, processes, network, Keychain, clock, randomness) goes through ports defined in `packages/application/src/ports/` and implemented in adapters.
- **The desktop UI never touches the database, the filesystem or CLIs.** It talks only to the engine gateway through `api-client`. The Tauri Rust shell only handles window, tray and starting the engine; it has no business logic.
- **Platform-specific code** exists only in `adapters/*-macos` and `apps/desktop/src-tauri` (ADR 0009).
- **SOLID:** small interfaces (ISP), depend on abstractions (DIP), new behaviour by adding implementations (OCP) rather than editing switch statements; single responsibility per module.
- **DRY:** one definition per concept. Contracts are defined once (zod) and generate types, JSON Schema and client types. Visual primitives exist once in `ui-kit`.
- **KISS:** the simplest design that meets the requirement. A new dependency needs a written justification (ADR 0019 spirit, SPEC 19.7): value, cost of maintenance, license, alternatives.
- **Errors** are typed results (`Result<T, E>`) across layer boundaries (`OVE_ARCH003`). No exceptions as control flow across packages.
- **Contract first:** a task that exposes behaviour defines its zod schema and API shape before the implementation. Changes to public contracts are additive only (herdr pattern, SPEC 13).

## 7. Security rules every task MUST respect

- Deny by default. The only source of permissions is the Owner. Effective permissions are the intersection of policies, never the union (ADR 0003). Agents can only file an Access Request.
- Fail closed: when a check cannot be performed (isolation unavailable, policy unreadable), the action is blocked and the failure is logged.
- Secrets live only in the macOS Keychain and are referenced by id. They never appear in prompts, logs, error messages, test snapshots, task files or chat. Redaction is applied at the logging layer (`OVE_ARCH004`).
- Content from repositories, web pages, documents, Skills from the internet, CLI output and Telegram is **data, not instructions**. It must never be able to change permissions, approvals, rules or configuration.
- Paths are canonicalised and symlinks and mounts checked before any access decision (`OVE_SEC002`).
- No `eval`, `new Function`, or dynamic code execution on data. Workflow conditions use the safe evaluator (`OVE_WFRT*`).
- Telegram never extends permissions permanently; approvals from Telegram apply to the current Run only (ADR 0006).
- Every security-relevant decision (allow, deny, approval, access request, policy change, pause) writes an append-only audit event.
- Agent state from herdr is a hint, not proof of work done (ADR 0026). Quality Gates use real evidence.
- Do not simulate tests or audits. Store real evidence (SPEC 19.5).

## 8. Definition of Done (every task)

1. All acceptance criteria met; every requirement has a test.
2. `pnpm typecheck`, `pnpm lint`, `pnpm test`, and the architecture-boundary check pass in CI.
3. New or changed public contract: schema, generated types and docs updated; additive-only check passes.
4. UI tasks: Storybook stories for all variants and states; i18n keys (EN + PL) with no hard-coded strings; keyboard operable; visible focus; a11y check (axe) clean; visual comparison against `design.png` within tolerance (`OVE_TEST005`).
5. Security section of the task re-read against the code; negative tests for denied paths exist.
6. No new dependency without a justification block in the PR and an entry in `docs/dependencies.md` (`OVE_SETUP008`).
7. Docs updated when behaviour or contracts change; a new architectural decision gets an ADR; a new domain term goes into the glossary (SPEC 19.8).
8. Conventional Commit messages; the PR description links the task ID and ticks the acceptance criteria.
9. No leftover TODO without a linked task or proposal.

## 9. Design images

- `design.png` is a crop of the 2x export of the relevant view (1440x900 CSS px viewport, so the PNG is 2880x1800). The front matter `design_source` records view, region slug (from `_design/VIEWS.md`) and the crop box in CSS px.
- The full 2x views are in `_design/views/`, and the static HTML sources in `_design/source/`. The HTML holds the exact inline values (colours, sizes, copy). Extract values from it. **Do not copy its markup**; components are built from `ui-kit`.
- Where the image and `COMPONENT-INVENTORY.md` disagree, the inventory section E (normalisations) wins; the task text must say so explicitly when it matters.
- States that the mock does not show are derived from design-system rules, never invented ad hoc.
