# OVE_DS108: Design-system documentation in MDX (tokens, usage rules, canvas boundary, contributing)

## 1. Summary

Writes the Storybook MDX documentation of the design system: token pages, usage rules (visibility is a word, state is icon + text, numbers carry units, limits say `wg CLI`, Approvals scope), composite catalogue with when-to-use, the canvas kit and React Flow boundary, DnD kit, the contribution guide and the extension recipes (new node kind, new state, new composite).

## 2. Context

Documentation is part of the Definition of Done and 'the project documentation is the source of truth' (ADR 0016). The kit must be easy for newcomers to extend (CONVENTIONS 6: SOLID/DRY/KISS). Language: docs in English (ADR 0017); Polish appears only in sample copy.

## 3. Scope (in)

- MDX pages in `docs/`: Overview, Tokens (colour, type, spacing, radius, glow, motion), Domain rules, State maps (agent/run/task), Composite catalogue (one entry per `ui:` capability with link to its story and props table generated by Storybook autodocs), Canvas kit, DnD kit, Accessibility (links OVE_DS104), Visual testing (links the visual tasks), Contributing.
- Recipes with code-shaped examples: add a node kind (touch `kinds.ts`, `CanvasNodeView` switch, palette entry, story, fixture), add an Agent state (touch `stateMaps`, label key, story matrix), add a composite (folder layout, needs/provides, G1..G7 checklist).
- Docs lint: broken-link check and a script that fails when an exported component has no story or no catalogue entry.

## 4. Out of scope

- Product documentation (apps/desktop), API docs of other packages.

## 5. Detailed requirements

1. Canvas boundary page (normative text): states that only `canvas/flow/**` imports `@xyflow/react`; lists exactly which responsibilities React Flow has (viewport transform, node drag/selection, handles/connections, custom node/edge hosting) and which are ours (dot grid, minimap, toolbar, routing, node/edge visuals, validation display, history); explains the controller seam and the pure `routeEdge`; states ADR 0019 (the editor draws, the engine executes) with a diagram of data flow `engine -> api-client -> CanvasModel -> kit`.
2. Domain rules page: visibility word (ADR 0028), state icon + text (E21), numbers with unit words, limits `wg CLI`, Telegram approves per Run only and permanent grants desktop-only (ADR 0003), Decisions never deleted (ADR 0008) so no delete affordance, untrusted text rendering (no `dangerouslySetInnerHTML`), `labels` props instead of hard-coded copy (G3).
3. Catalogue generation: a script lists `ui:` capabilities from the task front matter / component exports and checks each has an MDX/autodocs entry; output is a table `component | group | story | needs`. Fails CI on drift.
4. Contribution guide: folder layout, naming (`ui:<Name>`), fixtures rules (deterministic), story rules (G7), review checklist (G1..G7, a11y, visual baseline update procedure on the reference runner), how to propose a token change (never inside a composite task), how to record open design questions.
5. Examples use fictional data and Polish sample copy; code fences are TypeScript/TSX; every page has an `Last verified against` footer with the kit version (read from package.json at build).
6. GLOBAL RULE G1 (tokens): every colour, radius, spacing, border, glow and motion value comes from the `--om-*` CSS custom properties / typed `tokens` export of part 1 (`ui:tokens`). No raw hex or rgba literal in component CSS (inventory E12). Values quoted in this task are the token VALUES, for the reviewer.
7. GLOBAL RULE G2 (reuse): the primitives named in `needs` are imported, never re-implemented or copy-styled. If a primitive lacks a variant this task needs, do not patch it: record it in section 14 and use the closest variant (the linker raises it with part 1).
8. GLOBAL RULE G3 (strings): the component contains no user-visible copy. Every visible string and every `aria-label` is a prop (grouped in a typed `labels` object where there are more than two), so `apps/desktop` can feed i18n keys (EN default, PL first translation, OVE_ARCH011). Stories and fixtures use the Polish mock copy verbatim as sample data.
9. GLOBAL RULE G4 (a11y): correct role/name/state, full keyboard operation, the global `:focus-visible` ring (E19, never `outline: none` without replacement), minimum text size 10px (E17), control borders meet 3:1 via `line-control` (E18), state is never conveyed by colour alone (icon or word), animations disabled under `prefers-reduced-motion`.
10. GLOBAL RULE G5 (layout robustness): `box-sizing: border-box`, buttons/inputs `font: inherit` (E9), flex children that hold text get `min-width: 0`; single-line text that can overflow uses `white-space: nowrap; overflow: hidden; text-overflow: ellipsis` and a `title` (or tooltip) with the full value; multi-line text wraps with `overflow-wrap: anywhere` for paths and ids. Scroll happens inside panels, never on the page (styl-wizualny).
11. GLOBAL RULE G6 (API shape): named export `<Name>` and exported `<Name>Props`; function component; root element forwards `ref` and passes through `className`, `data-*` and native attributes in line with the part 1 convention; controlled where there is interactive state (`value`/`onChange`), with no internal data fetching, no timers other than documented animations, no global state.
12. GLOBAL RULE G7 (stories): Storybook CSF3 file with one story per variant and per state listed here (including the states the mock does not draw), a `Playground` story with controls, fixtures in `<Name>.fixtures.ts` (typed, deterministic, no `Date.now()`/random), and play-function interaction tests for every interactive behaviour.

## 6. Design notes

No design image. Visual reference of the docs structure is Storybook's default docs layout themed with the kit tokens.

## 7. Reuse

Uses Storybook autodocs and the part 1 theme; no new components. Capability naming and prop names follow part 1 (`ui:<ComponentName>`). New reusable pieces created here are listed in `provides` and must be consumed by later tasks instead of being copied.

## 8. Architecture and code placement

Layer: UI, presentational. Package `packages/ui-kit`, folder owned by this task. Depends only on React, the part 1 tokens and the primitives listed in `needs`; `ui-kit` imports nothing from `apps/*`, `api-client`, `contracts` or any other internal package (CONVENTIONS 6). Props are plain, serialisable view-models, so a feature in `apps/desktop` maps gateway data (the UI only talks to the engine through `api-client`) into them. SRP: one component per file, shared helpers live in the `common` group, never copied. Dependency direction: composite -> primitive -> token, never the reverse. Docs live next to the package (`packages/ui-kit/docs`), not in `docs/` of the repo root (project docs are separate, ADR 0016); a pointer page in project docs is out of scope.

## 9. Security and safety

UI-only component with no trust boundary of its own, but its props may carry untrusted data (agent messages, repository paths, CLI output, Telegram text). Therefore: all text is rendered as React text nodes; no `dangerouslySetInnerHTML`/`innerHTML`, no Markdown-to-HTML, no `eval`/`new Function`; link targets are rendered as links only for `https:`/`http:` or app-internal routes (anything else, e.g. `javascript:` or `data:`, is shown as inert text); external links carry `rel="noopener noreferrer"`. The component performs no action itself, it only calls `on*` callbacks; the owning feature enforces Approvals and permissions (ADR 0003). The display must never hide a security-relevant fact (visibility word, expiry, scope 'this Run only', origin channel). Docs must not include real credentials, paths or tokens; the Telegram/approval rules are documented exactly as ADR 0003 states so developers do not add a permanent-grant button to the bot.

## 10. Errors and edge cases

- A capability exists without an entry -> docs lint fails.
- Broken internal link -> docs lint fails.
- Docs claim a token value that differs from the token file -> tokens page is generated from the token export (no hand copying).
