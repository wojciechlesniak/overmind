# OVE_SHELL007: Provide the i18n provider: locale selection, namespace loading and formatting context

## 1. Summary

Wires the ARCH011 i18n infrastructure into the app: `I18nProvider` initialises i18next with EN (default) and PL, lazily loads the namespaces that the discovered feature manifests declare, suspends rendering until the current route's namespaces are loaded, keeps `<html lang>` in sync and exposes `useLocale()` and formatting helpers.

## 2. Context

ARCH011 delivers `initI18n({ locale, loadNamespace })`, typed `useT(ns)`, the formatters (`formatNumber`, `formatDate`, `formatRelative`, `formatBytes`, `formatDuration`...), the pseudo-locale `en-XA` and the lint. ADR 0017: code and default UI in English, Polish is the first translation; the mocks are Polish so Polish copy is entered by the owning feature task. The shell needs: locale detection, a place for the Owner's choice (App settings, SETUI), namespace loading driven by manifests (`namespaces: [...]`), a Suspense boundary, and a pluralisation-correct formatting context (Polish plurals: one/few/many/other, design rule 'numbers always with a word unit').

## 3. Scope (in)

- `I18nProvider` and `useLocale()` in `apps/desktop/src/app/providers/i18n-provider.tsx`.
- Locale resolution: stored choice -> OS language -> `en`.
- Namespace preloading for the current route (`ensureNamespaces(manifest.namespaces)`).
- `<html lang>` and `Intl` locale sync; dev-only `?locale=en-XA`.
- Shell namespaces and their JSON files: `shell` (rail/nav/generic), `topbar`, `shell-engine`, `shell-notify` (empty skeleton files with the keys each task adds are created by those tasks).

## 4. Out of scope

- Translations of feature views (each feature).
- The Language setting UI (SETUI; this task exposes `setLocale`).
- Engine-side strings (ARCH015).

## 5. Detailed requirements

1. Resolution order: (1) `localStorage['overmind.locale']` if `en|pl` (wrapped in try/catch, may be unavailable), (2) `navigator.languages` first match of `pl*` -> `pl`, else `en`. `setLocale(locale)` updates state, i18next language, `document.documentElement.lang`, and storage (best effort). Storage is a per-viewer convenience only (browser storage rule); the authoritative preference, if SETUI later stores one in engine config, overrides it at startup through the optional prop `initialLocale`.
2. Loading: the provider receives `namespaceLoaders` generated by ARCH009 (`locales/index.generated.ts`). `useRouteNamespaces(namespaces)` (used by OVE_SHELL010's route wrapper) calls `i18n.loadNamespaces` and suspends with a standard `React.use` promise until loaded for the active locale AND the `en` fallback. Always preloaded: `common`, `errors`, `a11y`, `shell`, `topbar`.
3. Fallback chain `pl -> en`, `en-XA -> en`; missing key behaviour is ARCH011 (dev `⟦missing:key⟧`, production EN string). The provider never renders a raw key in production.
4. `useFormat()` returns `{ number, date, time, relative, list, bytes, duration }` bound to the active locale; relative-time strings come from translations (`common:time.*`); dates are shown in the OS time zone. A dev-only warning fires if a component calls `new Date().toLocaleString()` (lint rule `no-restricted-properties`, added by proposal if absent).
5. Locale change at runtime re-renders consumers without a reload (i18next `languageChanged` event -> context value change). The tray window is a separate webview: it reads the stored value on its own focus; a live push between windows is not implemented (documented limitation).
6. Error boundaries and the engine-down screen must work BEFORE namespaces load: `shell-engine` and `common` are bundled eagerly (not lazy) so the app can explain a failure even if a lazy chunk fails.
7. Accessibility: `lang` attribute correct for screen readers; Polish plurals verified by test for the counts 1, 2, 5, 12, 22, 25 on `common:count.waiting` ('3 czekają').
8. i18n lint (`pnpm i18n:check`) passes for the shell namespaces; the pseudo-locale story renders the shell without hard-coded strings.

## 9. Security and safety

- Locale storage holds only `en|pl` (validated), never free text.
- Translation strings are static JSON shipped with the app; no remote loading (CSP `connect-src` forbids it); no HTML in strings (ARCH011 req. 3).
- Interpolated values (Workspace names, CLI text) are rendered by React as text; the `<Trans>` components set is limited to `strong|em|code|link` so injected markup is impossible.
- If storage is blocked the app still works (try/catch around every access).

## 10. Errors and edge cases

- Storage disabled: falls back to OS language each start.
- `navigator.languages` empty: `en`.
- Namespace chunk fails to load (disk corruption): Suspense error boundary shows the generic crash screen (SHELL019) using eager `common` strings.
- Locale switch while a route is loading: the new locale's namespaces load before re-render.
- Unknown stored value `fr`: ignored.

## 11. Acceptance criteria

- [ ] Given `navigator.language = 'pl-PL'` and no stored choice then the UI renders Polish and `<html lang='pl'>`.
- [ ] Given a stored choice `en` then English wins over the OS language.
- [ ] Given a route manifest declaring `['board']` then the namespace is loaded before the route renders (no flash of keys).
- [ ] Given storage throwing then the app starts without error.
- [ ] Given `?locale=en-XA` in dev then strings are pseudo-localised.
- [ ] Polish plural test passes.
